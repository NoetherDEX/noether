# Stellar-skills audit of Noether staging — 2026-07-22

**Method:** ultracode multi-agent audit. The official SDF Stellar developer skills from https://skills.stellar.org (`stellar/stellar-dev-skill`) were installed locally and used as the *checklist*. 13 finder agents (each reading the relevant skill file — smart-contracts development/security/testing, dapp, data, assets) swept the staging working tree area-by-area; every finding was then handed to an adversarial verifier that (a) re-read the cited code, (b) checked whether it was already handled or compensated elsewhere, (c) grepped `KNOWN_ISSUES.md`, `CLAUDE.md`, `docs/AUDIT-2026-06.md`, `docs/TASKS.md`, `docs/LIGHTER-GAP-2026-07.md`, `docs/THREAT_MODEL.md`, `docs/security/`, `docs/plans/` to reject duplicates, and (d) sanity-checked viability against project constraints (WASM ~128 KB ceiling, soroban-sdk 21 pin, ContractError variant ceiling, deliberate designs). 108 agents, ~7.5 M tokens.

**Result:** 65 confirmed (12 P1 · 24 P2 · 29 P3), 21 deduped as already-tracked, 9 refuted. No P0 — nothing is an actively-exploitable live drain; the P1s are pre-mainnet correctness/reliability defects, most with sub-day fixes.

**Two findings were re-verified by hand against the code** (not just relayed from the agent chain): the vault deposit-fee double-count (#2) and the stale NOE issuer fallback (#12) — both real.

Severity key: **P0** money-loss/live-exploit · **P1** fix before mainnet · **P2** meaningful improvement · **P3** polish. Effort: **S** <1d · **M** 1–3d · **L** >3d.

## Themes (read this first)

> **STATUS 2026-07-22 — Theme 1 RESOLVED.** All five vault/factory accounting bugs fixed on `staging` with regression tests. Verified: `noether_common` 27, `vault` 49, `vault_factory` 55, `market` 173 — all pass. Note surfaced during the fix: a fully-drained vault (AUM=0, NOE outstanding) is now deposit-locked by design and recovers via trader losses (`receive_loss`), not new LP deposits — a graceful admin supply-reset path is a possible follow-up but not required for correctness.

1. **Vault & factory share-price accounting — the standout NEW cluster (4 findings, all one-line fixes).** None of these were in the June audit. Deposit fees are double-counted into AUM so NOE price drifts up permanently (#2); and three separate "empty-pool-but-shares-outstanding" states mint new deposits 1:1 against dead shares, gifting up to half of a depositor's money to worthless legacy holders (#3 vault, #4 vault-factory) or letting a mark-spike deposit in at a zero share price (#3). Two P2s in the same file let `pay_bounty`/`reserve_for_position` spend the earmarked shortfall reserve (#16, #17). This is the highest value-per-hour work in the whole report.

> **STATUS 2026-07-22 — Theme 2 RESOLVED.** Fixed on `staging` with two discriminating regression tests. `market/src/position.rs` `aggregate_cross_positions` now values any unreadable/bogus price at `−size` (fail-closed) instead of silently dropping the leg's PnL — so the withdraw/open free-margin gates block on a dead feed rather than fabricating `+size` profit for shorts. `market/src/lib.rs` `liquidate_cross_account` now pre-scans every leg's price and returns `CrossMarginNotLiquidatable` if any is unreadable, so it never seizes funds on partial information; this also retires the unsound `i128::MAX/2` sentinel (resolves audit #14). No new error variants, negligible WASM. Verified: `market` 175 (was 173) — all pass; both new tests fail on the pre-fix code.

2. **Oracle-failure fail-safe is inverted on the cross-margin path (P1, small).** The sentinels substituted when a price is unreadable (`i128::MAX/2` on liquidation, `0` on withdraw/open) misvalue positions: a dead feed can falsely liquidate a healthy cross account's *other* legs, or let a short withdraw/lever against fictitious profit. `docs/LIGHTER-GAP` currently documents this exact behaviour as "fail-safe in both directions" — it isn't. Fix = value an unpriceable leg at max-loss and fail closed on liquidation (#1, #15).

3. **Nobody in the codebase handles Soroban state archival / restore (`restorePreamble`) — a whole missing capability class.** Testnet keeper traffic + resets keep entries hot so it never fires today; on mainnet a ~30-day-dormant position/order archives and every path hard-fails opaquely. Affects the keeper write path (#7 — silently wedges liquidations), the web + tx-builders build paths (#10), and the keeper TTL job never extends the WASM *code* entry at all (#8). This is the clearest "the skill knows something the repo doesn't" result.

4. **RPC error-classification / failover gaps (reliability).** The indexer doesn't classify HTTP 429/5xx as transient, so a rate-limited primary starves it despite configured failover — the same class as the 5-week indexer freeze, different classifier miss (#9). Web tells users a `TRY_AGAIN_LATER` tx "submitted" (#25). Hand-rolled confirmation loops abort on one transient error instead of using `rpc.pollTransaction` (keeper + web, #26/#33).

5. **The contract test suite is structurally blind to the top Soroban exploit class.** All 8 suites run under global `mock_all_auths()` with **zero** `env.auths()` assertions — deleting a `require_auth` from `close_position` or any admin setter leaves all ~390 tests green (#5). No TTL, fuzz, or upgrade-fork tests. All test-only, zero WASM cost, and directly relevant to the Security Audit Bank submission.

6. **Assets/SAC mainnet hygiene.** The web NOE issuer fallback is stale (`GCKIUOTK…`/admin) and derives a *different* SAC than the deployed NOE token (`GA7PCANK…`) — this already breaks local dev / any build without the env var set, because trustline checks and the changeTrust build target the wrong issuer (#12). No SEP-1 `stellar.toml` for NOE (#34); `fund_vault.sh` seeds via raw SAC transfer, bypassing all vault accounting (#35).

#### 5. [indexer] HTTP 429/5xx not classified transient — failover pool never rotates on rate-limit
- **Severity/effort:** P1 / S  ·  **Category:** correctness
- **Location:** `indexer/src/rpc.ts:141`
- **Skill rule:** stellar-data/SKILL.md § Best Practices → Rate Limiting (429 → exponential backoff; both RPC and Horizon are rate-limited)
- **Problem:** fetchEvents only treats 'TRY_AGAIN_LATER', 'ECONNRESET', 'ETIMEDOUT', and 'fetch failed' as transient. The stellar-sdk v14 http client surfaces HTTP failures as errors whose message is 'Request failed with status code 429' (or 503) with the status on err.response.status — none of which match, so the error is rethrown on attempt 0: no backoff, no pool.rotate(). The outer poll loop then retries the SAME endpoint every pollIntervalMs forever. On the documented rate-limited public testnet RPC (and any quota-limited mainnet provider) a persistently-429ing primary stalls the indexer even though SOROBAN_RPC_URLS failover is configured — the exact failure class behind the 2026-06→07 indexer freeze, just via a different classifier miss.
- **Fix:** In the transient check, also read the HTTP status: `const status = (err as { response?: { status?: number } })?.response?.status;` and treat `status === 429 || (status !== undefined && status >= 500)` (plus message match `/status code (429|5\d\d)/`) as transient so the existing rotate + exponential backoff path fires. Additionally rotate the pool once before the final rethrow so the next poll iteration starts on a different endpoint.
- **Verifier:** Factually verified. indexer/src/rpc.ts:140-144 classifies transient only via message substrings 'TRY_AGAIN_LATER'/'ECONNRESET'/'ETIMEDOUT'/'fetch failed'; line 145 rethrows anything else on attempt 0, BEFORE the rotate at line 146. The installed stellar-sdk is 14.6.1 and its Node build hard-selects the axios client (node_modules/@stellar/stellar-sdk/lib/http-client/index.js: `if (true) { require("./axios-client") }`); rpc/jsonrpc.js postObject does a plain `client.post` with no validateStatus override, so an HTTP 429/503 rejects with the axios error 'Request failed with status code 429' (status on err.response.status) — matching none of the four substrings. parseRetentionError also won't match it, so the error propagates to the poll loop, which at indexer/src/poll.ts:101-104 merely logs and sleeps pollIntervalMs — pool.current() is never rotated, so a persistently-429ing primary starves the indexer despite configured SOROBAN_RPC_URLS. Not handled elsewhere: the keeper's own classifier (scripts/keeper/src/stellar.ts:236) explicitly includes 429|502|503|504, proving the project treats these as transient — the indexer classifier just misses them. Not tracked: KNOWN_ISSUES.md, AUDIT-2026-06.md (I-3 is the original failover item, since implemented), TASKS, LIGHTER-GAP, THREAT_MODEL, docs/security, docs/plans contain no mention of the 429 classifier gap; docs/RPC.md:45 documents the current narrow trigger list as the feature. Suggestion is viable and small (extend classifier + one test, mirroring the keeper's regex). Same failure signature (classifier miss → poller stuck forever) as the 2026-06→07 freeze fixed in this very file. P1: pre-mainnet reliability on documented rate-limited endpoints; not P0 since no funds at risk and indexer stalls are recoverable after re-point. Effort S.


#### 6. [keeper] Write path never checks isSimulationRestore — archived entries wedge liquidations/orders
- **Severity/effort:** P1 / S  ·  **Category:** correctness
- **Location:** `scripts/keeper/src/stellar.ts:1126`
- **Skill rule:** stellar-dapp/SKILL.md § Transaction Building → Smart Contract Invocation + § Transaction Submission (simulate → prepare → sign → send → poll lifecycle; prepareTransaction 'simulates and applies footprint/auth/fees' — the restore branch of that lifecycle is unhandled)
